# RPG Tracker — инструкция от архива до живого сайта

Это доработанная версия именно исходного `rpg-tracker.zip` (Next.js 16 + React + TypeScript + Supabase). Не Vite и не новый проект.

**Важно:** приложение — готовый комплект исходников и SQL. Из рабочей среды удалось выполнить `tsc --noEmit` и ESLint без ошибок. Полная `next build` здесь не завершилась **из-за отсутствия подключения к npm для загрузки нативного Linux-модуля SWC**. Доступа к вашему проекту Supabase и учётным записям нет, поэтому боевую регистрацию, RLS и Vercel нужно проверить по инструкции ниже.

## Что реализовано

- Регистрация, вход, подтверждение email по ссылке, выход.
- Создание заявки игроком (имя, HP, обязательный портрет).
- Статусы pending / approved / rejected / archived.
- Общая галерея **только одобренных** героев, профиль и три колонки карт.
- Административная панель, одобрение / отклонение, архивация, удаление.
- Урон (сначала расходуется броня), лечение, назначение количества брони.
- Все операции HP/брони проводятся атомарно в PostgreSQL и попадают в журнал.
- Добавление, редактирование, удаление карт только администратором.
- Подписка на Supabase Realtime для обновления открытых страниц.
- RLS для персонажей, карт, журнала и загрузки картинок.

## Перед началом: очень важные предупреждения

1. **Сделайте копию исходного проекта и экспорт текущей базы.** Файл `supabase/01_setup.sql` удаляет *старые RLS-политики* таблиц приложения и создаёт новые. Персонажей он не удаляет, но на другой схеме базы может потребоваться адаптация.
2. **Никаких секретов в GitHub.** `.env.local` специально не включён в готовый архив. Ваш старый `.env.local` остаётся у вас, но не должен попадать в Git.
3. **Новый SQL рассчитан на существующие поля** `characters`: `id uuid`, `user_id uuid`, `name text`, `max_hp integer`, `current_hp integer`, `armor integer`, `status text`, `image_url text`, `created_at timestamptz`. Впервые созданной таблице все эти поля будут добавлены автоматически. Если старая таблица отличается — сначала исправьте схему, не запускайте SQL вслепую.
4. **Изображения публичные.** Пользователи не видят анкету до одобрения, но любой, кто получил прямую ссылку на файл из публичного бакета, сможет открыть картинку. Для строгой конфиденциальности ожидающих анкет требуется отдельная версия с приватным бакетом и signed URL.
5. **Механика брони — расходуемая.** Если поступило 8 урона при броне 5, броня станет 0, а HP уменьшится на 3. Если по правилам игры броня постоянная, SQL-формулу надо заменить.

## Этап 1. Подготовка на Windows

1. Установите Node.js (20.9+; лучше актуальную LTS), Git и Visual Studio Code.
2. Создайте резервную копию оригинальной папки `rpg-tracker`.
3. Распакуйте **готовый ZIP** в отдельную папку (например `C:\Projects\rpg-tracker`). В нём уже находятся **полные файлы по нужным путям**. Не надо вставлять кусочки кода по памяти.
4. В VS Code нажмите **File → Open Folder** и выберите папку с `package.json`.
5. Откройте **Terminal → New Terminal** и выполните:

```powershell
node -v
npm -v
npm ci
```

`npm ci` загружает пакеты по исходному `package-lock.json`. Прежнюю папку `node_modules` копировать не нужно.

**Проверка:** команда `npm ci` завершается без ошибки.

## Этап 2. Привязка Supabase и настройка структуры

**Файлы:** `supabase/00_diagnostics.sql`, `supabase/01_setup.sql`, `.env.local.example`.

1. В Supabase откройте существующий проект → **SQL Editor**.
2. Выполните **весь код** файла `supabase/00_diagnostics.sql` (read-only). Сверьте поля и типы таблицы `characters` с предупреждением выше.
3. Создайте резервную копию схемы и данных (через доступные инструменты Supabase / PostgreSQL; не полагайтесь только на возможность отмены SQL).
4. Выполните **весь код** `supabase/01_setup.sql` в SQL Editor **одним запуском**. Если он выдаёт ошибку, не переходите дальше: нужно проверить исходную схему и состояние базы.
5. В разделе **Storage** убедитесь, что есть бакет `character-images` со статусом Public, форматами JPEG/PNG/WebP и ограничением 3 MB.
6. В разделе **Database → Publications** проверьте, что таблицы `characters`, `character_cards`, `character_actions` входят в `supabase_realtime`.
7. Откройте **Project Settings → API Keys** или актуальный раздел API настроек. Возьмите URL и публичный ключ (`anon` или `publishable`).
8. Скопируйте `.env.local.example` в новый `.env.local` и замените заглушки. Формат:

```dotenv
NEXT_PUBLIC_SUPABASE_URL=https://YOUR_PROJECT_REF.supabase.co
NEXT_PUBLIC_SUPABASE_ANON_KEY=YOUR_PUBLIC_KEY
```

**Никогда** не вставляйте туда secret/service_role key.

**Проверка:** таблицы `character_cards`, `character_actions`, `admins` существуют; `characters` осталась с прежними персонажами; в SQL нет ошибок.

## Этап 3. Локальный запуск и авторизация

**Файлы:** `src/proxy.ts` (вместо удалённого `middleware.ts`), `src/lib/supabase/middleware.ts`, `src/app/auth/signout/route.ts`, `src/app/auth/confirm/route.ts`, `src/app/login/page.tsx`, `src/app/layout.tsx`, `src/app/globals.css`.

1. Выполните:

```powershell
npm run dev
```

2. Откройте `http://localhost:3000`.
3. Перейдите на `/login`, зарегистрируйтесь тестовым email.
4. Если в Supabase включено **Confirm email**, для использования ссылок подтверждения настройте в **Authentication → URL Configuration** `http://localhost:3000` как Site URL и разрешённый redirect `http://localhost:3000/auth/confirm`. Убедитесь, что Supabase может отправлять письма на ваш тестовый адрес (встроенная SMTP-почта ограничена).
5. При желании для закрытого локального теста временно отключите подтверждение email в настройках Auth, понимая, что на публичном сайте это не лучший вариант.
6. Войдите, откройте `/dashboard`, выйдите через кнопку «Выйти».

**Проверка:** логин, выход и повторный вход работают. Кнопка выхода не даёт ошибку 404.

## Этап 4. Первый администратор

**Файл:** `supabase/02_make_admin.sql`.

1. Зарегистрируйте на сайте учётную запись будущего администратора (можно уже созданную).
2. В `supabase/02_make_admin.sql` замените `REPLACE_WITH_ADMIN_EMAIL@example.com` на **реальный email** этой учётной записи.
3. Выполните SQL в **SQL Editor** Supabase.
4. Выйдите из аккаунта и снова войдите (или обновите страницу).
5. Откройте `http://localhost:3000/admin`.

**Проверка:** администратор видит панель. Обычный игрок получает редирект в личный кабинет. Проверка роли происходит **в Supabase**, а не только по кнопке на странице.

## Этап 5. Заявки и профили персонажей

**Файлы:** `src/app/dashboard/CreateCharacterForm.tsx`, `src/app/dashboard/page.tsx`, `src/app/page.tsx`, `src/app/character/[id]/page.tsx`, `src/lib/types.ts`.

1. В аккаунте игрока откройте `/dashboard`.
2. Введите имя персонажа, максимальное HP, выберите JPEG/PNG/WebP не больше 3 MB.
3. Нажмите «Отправить на модерацию».
4. Проверьте, что у игрока персонаж появился со статусом «На модерации», а на главной его нет.
5. Войдите администратором, откройте `/admin`, одобрите заявку.
6. Проверьте главную страницу и клик по карточке: должно открыться `/character/UUID`.

**Проверка:** персонаж виден всем после одобрения; чужую ожидающую заявку игрок не видит.

## Этап 6. Урон, броня, лечение, карты и модерация

**Файлы:** `src/app/admin/layout.tsx`, `src/app/admin/page.tsx`, `src/app/admin/ModerationButtons.tsx`, `src/app/admin/characters/[id]/page.tsx`, `src/app/admin/characters/[id]/AdminCharacterActions.tsx`, `src/app/admin/characters/[id]/CardManager.tsx`.

1. В админке нажмите **Управлять** рядом с одобренным персонажем.
2. Пример: у героя 20 HP, установите броню 5.
3. Укажите 8 и «Нанести урон». Результат: **17 HP, 0 брони**.
4. Укажите 10 и «Вылечить». Результат: **20 HP** (не выше максимума).
5. Создайте по карте трёх типов: «Урон», «Защита», «Лечение».
6. Откройте публичную страницу персонажа, убедитесь, что карта попала в нужную колонку.
7. Попробуйте отредактировать название/описание карты, затем удалить одну из карт.
8. Попробуйте архивировать персонажа, восстановить его, отклонить новую заявку и при необходимости удалить тестового персонажа.

**Проверка:** изменять HP и карты может только администратор; изменения характеристик есть в журнале.

## Этап 7. Синхронизация в реальном времени

**Файл:** `src/components/RealtimeRefresh.tsx`.

1. Откройте сайт в двух браузерах или в обычной и приватной вкладке.
2. В первой вкладке войдите администратором. Во второй — игроком.
3. Откройте одну и ту же страницу персонажа.
4. В первой вкладке измените HP или добавьте карту.
5. Во второй вкладке изменения должны отобразиться без нажатия F5.
6. Если вкладка спала и пропустила обновления, при возвращении на вкладку приложение повторно запрашивает актуальные данные.

**Проверка:** оба пользователя видят одинаковые значения. Если нет — проверьте публикацию `supabase_realtime`, RLS и сообщения консоли браузера.

## Этап 8. Проверка качества перед выкладкой

Остановите `npm run dev` комбинацией **Ctrl+C**. Выполните:

```powershell
npm run lint
npx tsc --noEmit
npm run build
npm run start
```

Откройте `http://localhost:3000` и повторите базовые проверки. **Не публикуйте**, пока `npm run build` не завершится успешно.

Обязательно протестируйте отдельные роли: пользователь А, пользователь Б, администратор, гость. Нельзя проверять безопасность исключительно кнопками — попытки изменения через прямые обращения к базе также должны отклоняться RLS.

## Этап 9. GitHub и публикация на Vercel

1. Не публикуйте `.env.local`, `node_modules`, `.next`. Они игнорируются `.gitignore`.
2. Создайте приватный репозиторий на GitHub.
3. Откройте терминал в папке проекта:

```powershell
git init
git add .
git commit -m "RPG Tracker MVP"
git branch -M main
git remote add origin https://github.com/YOUR_USERNAME/rpg-tracker.git
git push -u origin main
```

Если в папке Git уже настроен, пропустите `git init` и `git remote add origin` либо сначала проверьте `git remote -v`.

4. На `vercel.com/new` импортируйте GitHub-репозиторий. Framework: **Next.js**, Root Directory: папка с `package.json`.
5. В **Settings → Environment Variables** добавьте те же **два публичных** значения, что в `.env.local`.
6. Запустите Deploy.
7. Получив действительный URL `https://...vercel.app`, добавьте его в **Supabase Authentication → URL Configuration** как Site URL и разрешите `https://...vercel.app/auth/confirm` как redirect.
8. Для регистрации посторонних игроков потребуется **собственный SMTP-провайдер** либо другой поддерживаемый Supabase метод регистрации. Встроенная отправка почты не рассчитана на массовую публичную регистрацию.
9. Проверьте реальное развёртывание со смартфона и браузера другого пользователя.

**Результат:** сайт доступен по общему URL; один Supabase-проект хранит одинаковые характеристики для всех.

## Отладка типовых ошибок

| Симптом | Что проверять |
| --- | --- |
| `Invalid API key` | `.env.local`, имена переменных, ключ именно от нужного проекта |
| `relation ... does not exist` | Запуск `01_setup.sql` в нужном Supabase-проекте |
| `new row violates row-level security policy` | Пользователь вошёл? папка изображения начинается с `user.id/`? SQL-политики установлены? |
| `permission denied for function` | SQL-функции созданы полностью и выданы GRANT EXECUTE |
| Админка недоступна | `02_make_admin.sql` и правильный email, повторный вход |
| Письмо регистрации не приходит | Настройки Supabase SMTP / Confirm email / Site URL |
| HP обновляется только после F5 | `supabase_realtime`, таблицы в публикации, RLS и соединение |
| `next build` падает | Сначала запустить `npx tsc --noEmit`, затем прислать полный вывод build |
| Блокировка изображения | MIME/размер до 3 МБ, публичный бакет, политики `storage.objects` |

## Полный код каждого файла

В том же пакете находится **`ПОЛНЫЙ_КОД_ПО_ФАЙЛАМ.md`**: он содержит полный текст всех новых и заменённых файлов, включая SQL. Каждый раздел начинается с точного пути, затем следует полный блок кода. Можно копировать содержимое блока целиком. Но гораздо проще распаковать готовый ZIP: структура папок уже собрана.
